## 0. 絶対条件（これに反したら失敗）

- **サブエージェント・子エージェント・別モデルへのタスク委譲・調査の並列分割は一切禁止**。
  あなた自身ひとつの文脈だけで調査・分析・執筆を完結させること。
- **読み取り専用**: コード・ドキュメントの変更、コミット、push、PR・Issue の作成、
  ファイルの削除・移動は禁止。検証コマンド（`npm test` / typecheck / web export 等）の
  実行は可とするが、環境制約で必ず失敗するもの（iOS ビルド、Simulator 操作、
  `npm install` / `pod install` 等のネットワーク依存）は試さないこと。
- 判断の根拠は必ず **ファイル:行** で示す。推測と事実を分離し、分からないことは
  「要確認」として報告。既存の報告書・判断保留リストを鵜呑みにせず、実コードで裏取りする。
- 新規パッケージ追加・`expo prebuild` の提案は、設計判断が必要なものとして「要確認」に回す。

## 2. レビュー視点（全セクションを出力する）

### 2.1 全体像
- 何を作っているか / 現在のフェーズ / コアフロー（録音→文字起こし→要約→詳細→Ask AI→
  エクスポート）の実装度 / 主要モジュールと依存関係 / 実用度スコア 57/100 の内訳が妥当か

### 2.2 課題（現状の問題）
- 未実装導線（「準備中」「現在利用できません」の残り）、エラー処理の穴、
  prohibitions 違反の残り、fontSize 直書き・hitSlop 未達・フォント方針衝突などの
  判断保留事項、テスト不足、データ・状態管理の負債、実機未検証リスク

### 2.3 改善提案（コード・設計）
- 「こうしたほうがいい」を優先度付きで。小（即効・低リスク）/ 中 / 大（設計変更）に分け、
  影響範囲・期待効果・検証方法を添える。トークン化・a11y・エラー UX など具体例を挙げる

### 2.4 機能提案（プロダクト視点）
- 「こういう機能があるとよい」をユーザー価値 × 実装コスト × 時期で評価。
  Ask AI（対象指定・コピー・音声入力）、会議キャプチャ、書き出し/共有、設定、
  オフライン挙動、オンボーディングなど。ロードマップ案（次にやるべき順）も示す

### 2.5 開発効率
- ブランチ / PR / CI 運用、ドキュメント更新の仕組み、エージェント運用
  （Sol / Luna / OpenCode / Claude の役割分担）、worktree 並列開発、自動化の余地、
  いちばん時間を食っているボトルネックの推測と解消策

### 2.6 リスク・配信
- ストア配信（署名・App Group・審査）への道、実機 QA 計画、共有ストア実データ移行、
  セキュリティ・プライバシー（API キーの扱い、ログ・transcript 漏えい、権限）の確認

## 3. 出力形式

- 日本語・Markdown。冒頭にエグゼクティブサマリ（最重要3点を3行で）
- 各視点は「現状 / 問題・提案 / 根拠（ファイル:行）/ 規模 / 優先度」の表で整理
- 最後に「次の30日でやるべき TOP10（順位・理由・見積もり規模・依存関係）」と
  「判断保留・要確認リスト」を付ける
- 分量は情報密度優先とし、過剰に長くしない（目安: 4000〜8000字程度）

## 4. 完了条件

- 上記 2.1〜2.6 すべてに言及している
- 各所見にファイル:行 の根拠がある
- サブエージェントを使っていない（使った形跡・言及が無い）
- コード・リポジトリ状態を一切変更していない
