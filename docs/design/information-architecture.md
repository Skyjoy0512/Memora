# Memora 情報設計

作成日: 2026-07-26
前提: `docs/reviews/current-ui-ux-audit.md` の監査結果

## 設計の出発点

現状の情報設計は**データ構造**（ファイル / タスク / 設定）に沿っている。しかしユーザーの認知は**目的**に沿う。

Memora におけるユーザーの目的は3つに集約される。

1. **録る** — 会議が始まる。すぐ録音したい
2. **読む** — 終わった会議の要約・文字起こしを見たい
3. **使う** — そこから出たタスクを片付けたい、過去の記録を探したい

情報設計はこの3つを反映すべきである。

## 中核となる概念モデル

```
Project（案件・分類軸）
  └── Meeting（会議 = 中核エンティティ）
        ├── Recording（音声。Meeting に内包される）
        ├── Transcript（文字起こし）
        ├── Summary（要約・キーフレーズ）
        └── Task（抽出されたやること。Meeting が出典）
```

**重要な決定: 「File」という概念を UI から廃止する。**

現状は File が中核エンティティになっているが、ユーザーが認知しているのは「会議」であって「ファイル」ではない。音声ファイルは Meeting の属性であり、独立した概念として見せる必要がない。インポートした音声も「会議」として扱う（種別が異なるだけ）。

これにより C-3（Project / Meeting / File / Task の関係が不明瞭）の根本原因が消える。File と Meeting の二重概念が無くなるためである。

## 案1: Capture 中心型

録音を最優先し、タブバー中央に録音 CTA を常設する。

```
Tabs: [ホーム] [ライブラリ] (●録音) [タスク] [設定]
```

- **ホーム**: 今日の状況。処理中・最近の会議・未完了タスクのダッシュボード
- **ライブラリ**: 会議一覧 + 検索 + プロジェクト絞り込み
- **録音**: 中央の独立した CTA。タブではなくアクション
- **タスク**: 全会議横断のタスク
- **設定**: 設定・アカウント・プラン

**思想**: 「録る」が最優先。中央 CTA は常に同じ位置にあり、どこからでも1タップで録音に入れる。

## 案2: Library 中心型

会議一覧を起点にし、録音はライブラリ内の CTA とする。

```
Tabs: [会議] [プロジェクト] [タスク] [設定]
```

- **会議**: 一覧が起点。上部に録音 CTA、検索は常設
- **プロジェクト**: 案件ごとの整理
- **タスク**: 横断タスク
- **設定**: 設定

**思想**: 蓄積された記録の再訪を最優先。Notion / Evernote に近い発想。

## 案3: Home ダッシュボード中心型

ホームを情報ハブとし、全てをそこから辿る。

```
Tabs: [ホーム] [検索] [タスク] [設定]
```

- **ホーム**: 録音 CTA + 処理中 + 最近 + プロジェクト + タスク要約を1画面に集約
- **検索**: 全文検索専用
- **タスク**: 横断タスク
- **設定**: 設定

**思想**: 情報を1箇所に集約し、タブ移動を減らす。

## 評価

各案を10観点で評価する（◎ 優 / ○ 良 / △ 可 / × 不可）。

| 観点 | 案1 Capture | 案2 Library | 案3 Home |
|---|---|---|---|
| 録音開始速度 | ◎ どこからでも1タップ | △ 会議タブへ移動が必要 | ○ ホームなら1タップ |
| 過去会議の探索性 | ○ ライブラリが独立 | ◎ 一覧が起点 | △ 検索タブ経由のみ |
| タスク管理の分かりやすさ | ○ 独立タブ | ○ 独立タブ | ○ 独立タブ |
| プロジェクト整理 | ○ ライブラリ内で絞り込み | ◎ 独立タブ | △ ホーム内セクション |
| 初回利用時の理解しやすさ | ◎ 中央 CTA が目的を語る | △ 空の一覧から始まる | ○ ダッシュボードが導く |
| 片手操作 | ◎ 中央下部 CTA | △ 上部 CTA | ○ 画面内 CTA |
| 将来の拡張性 | ○ ライブラリに機能追加可 | ◎ 概念が分離済み | × ホームが肥大化する |
| 実装複雑度 | △ 中央 CTA が要設計 | ◎ 標準的なタブ | ○ 標準的 |
| HeroUI Native との親和性 | ○ 標準部品で構成可 | ◎ ListGroup / SearchField が活きる | ○ Card 中心 |
| 認知負荷 | ◎ 目的が3つに整理される | ○ 概念が明確 | × 1画面の情報量が過大 |

### 案3 を却下する理由

ホームに全てを集約すると、**会議が増えるほどホームが破綻する**。現状の HomeScreen（393行）が既に検索・プロジェクト・一覧・空状態を抱えており、ここにタスク要約と処理中を足すと認知負荷が上限を超える。「将来の拡張性 ×」「認知負荷 ×」は致命的である。

### 案2 を却下する理由

情報整理としては最も筋が良い（プロジェクトが独立し、拡張性が高い）。しかし **Memora の中核価値である「録る」が二級市民になる**。会議タブに移動してから録音 CTA を押す構造は、「会議が始まったのですぐ録りたい」という最も切迫した状況で1ステップ余分になる。「録音開始速度 △」「片手操作 △」は Memora では許容できない。

また初回利用時、空の一覧から始まるのは体験として弱い。

### 採用: 案1 Capture 中心型

**理由:**

1. **Memora の中核価値がナビゲーション構造に表れる。** 中央の録音 CTA は、アプリを開いた瞬間に「これは録るアプリだ」と伝える。監査の C-1 を根本から解決する
2. **片手操作に最も適する。** 最高頻度かつ最も切迫した操作が、親指の自然な位置にある
3. **ライブラリを独立させることで探索性を確保する。** 案2 の利点（会議一覧の独立）を、タブ枠を1つ使うだけで取り込める
4. **ホームを軽く保てる。** ダッシュボードは「今の状況」に限定し、一覧はライブラリに委ねられる

**案1 の弱点と対策:**

- 弱点: 中央 CTA の設計が非標準で実装複雑度が上がる
- 対策: タブではなく**アクションとして扱う**。`app/(tabs)/_layout.tsx` のカスタム `tabBar` で中央にボタンを描画する現行方式を踏襲し、Expo Router のタブ定義には含めない。これにより「タブ選択状態」の概念と衝突しない

- 弱点: プロジェクトが独立タブを持たない
- 対策: ライブラリ内の絞り込み軸として提供する。プロジェクト数が増えた場合はライブラリ内にプロジェクト一覧ビューを設ける

## 採用する情報設計

### Bottom Tabs（4タブ + 中央アクション）

| 位置 | 名称 | 責務 |
|---|---|---|
| 1 | **ホーム** | 今の状況。処理中・最近の会議・未完了タスクの要約 |
| 2 | **ライブラリ** | 会議一覧・検索・プロジェクト絞り込み |
| — | **録音**（中央アクション） | 録音の開始。録音中は状態表示に変化 |
| 3 | **タスク** | 全会議横断のタスク |
| 4 | **設定** | 設定・アカウント・プラン |

### タブ名称の根拠

`apple-design` の原則「Direct, specific labels beat safe generic ones」に従い、内容を表す名称にする。

- 「ホーム」→ 内容を表さないが、ダッシュボードの慣習として許容。代替案「今日」も検討したが、日付に限定されない情報を含むため不採用
- 「Ask」を廃止 → AI 質問は会議詳細内の文脈付き機能へ移す（監査 C-2）
- 「ファイル」を廃止 → 「ライブラリ」（会議の蓄積）へ

### 概念の対応

| 旧 | 新 | 理由 |
|---|---|---|
| File | **Meeting** | ユーザーが認知しているのは会議。音声ファイルは属性 |
| Ask（タブ） | Meeting 詳細内の Ask | 文脈がないと使えない機能のため |
| プロジェクト（ホーム内表示切替） | ライブラリの絞り込み軸 | 分類軸として明示 |
| メモ（詳細内タブ） | Meeting 詳細内のセクション | タブを消費するほどの独立性がない |

### 廃止する画面

- `app/(tabs)/ask-ai.tsx` — 会議詳細内へ移設
- `app/preview.tsx` — 開発用。ビルド構成で分離
- `app/dev-fonts.tsx` — 開発用。ビルド構成で分離

### 追加する画面

- ライブラリ（会議一覧・検索）
- 録音セットアップ
- 録音中
- 処理中（グローバル状態）
- プロジェクト詳細
- 権限設定
- サブスクリプション
